## 第一部分 · 现有不足

### A. 数据准确性

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| A1 | **同一首屏出现三个互相矛盾的"轻微变化"数字** | 首屏大字「存在 **26** 处轻微变化」（步骤级）／建议操作「**16** 处轻微变化无需处理」（分组级）／分节标题「**16** 组可接受差异（共 **24** 个步骤）」。而 Tab 标签又写「本轮 16 组（**26 步**）」 | 客户第一屏就遇到 26 / 16 / 24 三个数，无法判断到底有多少问题 |
| A2 | **分组步数合计对不上，存在 2 步"账目黑洞"** | `stats.minorSteps = 26`；`items` 共 16 条，全部 `kind=minor`，`affectedSteps` 求和 = **24**。有 2 个被判轻微变化的步骤没有归入任何问题组 | 聚类/去重逻辑丢步数，结论不可自证 |
| A3 | **结论动词自相矛盾** | 首屏 headline「存在 26 处轻微变化，**无需处理**」；副标题「26 步存在可接受差异，**建议业务确认**」；`shipAdvice=confirm`「建议确认可接受差异后发布」 | 内部 verdict 是 `attention`（需人工确认），但文案写死"无需处理"，客户会得到"不用管"的错觉 |
| A4 | **合格率 100% 的分母排除了轻微变化** | `stats.passRate = 1`，而 `passSteps=18 / minorSteps=26 / regressSteps=0`，即 `18/(18+0)` | 明明 26 步有差异，合格率却是 100%。该字段会被飞书通知 / CI 消费，是典型的"口径粉饰"风险点 |
| A5 | **同一页面、同一差异率，跨报告给出相反判定** | 9/8 报告：审批筛选 `0.70%` → **需修复**；9/9 报告：同一页面同一 `0.70%` → **无需处理**。报告只用一句"状态改善"带过，未说明原因（基线更新？判定参数变更？） | 判定不可复现，直接摧毁客户对报告的信任 |
| A6 | **变化性质在三个位置给出三种说法** | 卡片标签「**内容变化**」；分组标题「多为**位置偏移**、显示效果或测试数据变化」；结论文案「差异主要为**位置偏移或渲染抖动**，非样式回归」 | 与"性质优先于差异率"的设计主张直接冲突：真正起决定作用的性质字段，在展示层被写成了三个互相打架的词 |
| A7 | **AI 审计层与像素层的结论互不引用，甚至相左** | AI 审计 `summary.json`：`total=4, pass=0, review=4`（含 occlusion「表格最后一行被分页栏遮挡，无法完整阅读」、layout 错位）；同一批页面的像素报告：`regressSteps=0`，「本次未发现需要修复的问题」 | 客户只看到"0 需修复"，看不到 AI 已发现的可用性问题；两份报告各自成立、合起来矛盾 |
| A8 | **AI 审计低置信度结论未做区分** | issue `confidence` 实测 0.5 / 0.62，与 severity=warning 混排展示，无置信度标识、无过滤阈值（虽有 `dropNoiseBelow` 配置但未在报告体现） | 客户无法判断哪条结论可信，"AI 说的"被当成确证 |
| A9 | **内部术语泄漏到客户文案** | 「页面结构与**监控区域**文案均与基线一致」「非**样式回归**」「渲染抖动」；`item.key` 含真实租户标识 `by-account/800187_hoymiles_com`；环境名 `Stage9084`、`DEV环境` 未解释 | 客户读不懂；租户标识属信息暴露面 |
| A10 | **内部迭代计数泄漏** | Tab 标签「可接受差异 · 本轮 16 组（26 步）／**历史 30 次**」 | 与设计文档"迭代历史 Tab 已移除，客户只关心本次结果"相悖，只是换了个位置残留 |

### B. 结构逻辑

| # | 问题 | 说明 |
|---|---|---|
| B1 | **按"页面"组织，而非按"问题"组织** | `ui-regression-customer.html` 含 96 个页面卡片、634 个标注框（**全部为 mark-benign**）、288 个视图切换按钮、3613 个文本节点。16 个问题被稀释在 96 屏证据里，客户要自己翻找 |
| B2 | **无差异项与有差异项平权铺开** | 18 步"完全一致"与 26 步"有差异"占用同等版面与交互权重，默认全部展开 |
| B3 | **run-drift 被加回客户报告** | 首屏出现「1 个业务流程状态恶化（…完全一致 → 轻微变化）· 1 个…状态改善（…明显衰退 → 轻微变化）」。而 `ui-regression-report-for-customer.md` §4 明确将「两次运行间对比（run-drift）」列为**刻意移除项**，理由正是"内部稳定性信号，会与衰退概念混淆" | 
| B4 | **DEV 环境与验收环境并列进结论** | 分环境表：预发布 4/4、Stage9084 28/30、UAT 2/4、DEV 10/15，四者平权汇总成"建议发版"。DEV 是开发自测环境，其差异与本次发版无关，却参与稀释整体结论 |
| B5 | **四套状态术语并行，无映射** | 客户报告 `pass/minor/regress/uncovered`；AI 审计 `pass/review/fail/skipped`；内部 `blocker/warning/noise/info`；CI gate 又单独读 `issuesReport.blocker`。同一个"不通过"有四种叫法，跨文档对齐成本高 |
| B6 | **覆盖率口径单一且易被误读** | 「检测覆盖 83%」= 有基线的步骤占比（44/53），与"质量被验证的比例"是两回事。AI 审计层 94/100 缺判定依据（skipped）这一事实完全没反映在客户报告的覆盖率里 |
| B7 | **问题卡片缺少"新增 / 历史遗留"标记** | 客户无法区分"本次发版引入"和"上次就有、尚未修"，直接削弱报告的归因价值（而这恰恰是衰退检测最该回答的问题） |

### C. 衰退洞察的呈现清晰度

| # | 问题 | 说明 |
|---|---|---|
| C1 | **只答"哪里变了"，不答"变成了什么、影响谁"** | 全部 16 条文案都是「页面有 N 处小范围内容变化，最大在页面上部，不影响整体布局」这类模板句。没有一条说明：变更前是什么、变更后是什么、用户会看到什么异常 |
| C2 | **AI 审计已有的"影响描述"能力没有回流到客户报告** | AI 审计能产出「表格最后一行被底部分页栏遮挡，仅露出半行文字，无法完整阅读」这种真正有用的业务语言，却被隔离在另一份报告里。客户报告里最有洞察的一句话，反而来自不面向客户的那一层 |
| C3 | **可用性缺陷与位移抖动被归为同一个"轻微变化"** | "遮挡导致无法阅读"与"整体平移 9px"对业务的影响差了两个数量级，但在客户报告里同为"可接受差异，建议确认"。严重度维度缺失，等于把洞察抹平 |
| C4 | **差异率被当作主指标展示** | 2.27% / 0.70% / 0.56% 作为卡片主要数字。而设计文档 §3 的核心主张恰恰是"差异率无法区分内容变化与位移"——文档里举的例子是 1.23% 不用管、0.82% 要修。把已被自己否定的指标放在最显眼处，客户必然按百分比直觉判断 |
| C5 | **无趋势、无回归曲线** | 没有"该页面近 N 次运行的分级变化"视图。衰退是时间序列概念，单快照报告天然缺失"是否在持续恶化"这一最关键洞察 |
| C6 | **无"修复优先级"排序** | 16 条按差异率降序排列，而不是按业务影响排序。客户拿到的是"像素变化排行榜"，不是"该先修什么" |
| C7 | **无验收动作出口** | 卡片有「登记问题」「看对比图」，但没有"接受为新基线 / 转工单 / 标记预期变更"的动作，报告看完后无法闭环 |

### D. 客户可读性

| # | 问题 | 说明 |
|---|---|---|
| D1 | **阅读指南位置靠后且避重就轻** | 「阅读指南（30 秒看懂）」在首屏结论之后，三条分别讲颜色、看图、待建基线——唯独没解释最容易困惑的 26/16/24 三个数字的区别 |

## 第二部分 · 优化建议

### E. 内容侧重：从"变化检测"转向"影响陈述"

**E1. 每条问题强制三段式，缺一段不予输出**

```
【哪里】  审批列表页 · 表格区域（第 3 屏中部）
【变成什么】表格最后一行被底部分页栏压住，只露出半行文字
【影响】  用户无法查看/点击最后一行的审批单 —— 会阻断操作
【建议】  需修复后再验收（非本次需求变更）
```

> 现有文案全部是"位置 + 变化率"的两段式，缺的正是"变成什么"和"影响"。AI 审计层已经具备生成这两段的能力（`ui-audit` 的 `description` 字段），直接复用即可。

**E2. 把 AI 审计结论作为"影响说明"注入像素问题的卡片，而不是另开一份报告**
- 像素层回答"哪里变了"（定位准）
- AI 层回答"变成什么、影响什么"（语义强）
- 合并后一份报告即可闭环，消除 A7 的双报告矛盾

**E3. 增加"新增 vs 历史遗留"标签**
- 用 `dedupeKey + 上次运行 verdict` 判定：`本次新增` / `上次已有·未修` / `上次已有·已确认接受`
- 首屏默认只展示"本次新增"，历史遗留折叠——直接回答"这次发版到底引入了什么"

**E4. 增加归因提示**
- 若某差异在多个环境同时出现（如 Stage9084 + UAT + DEV），标注「跨环境共现，疑似公共组件/配置变更」
- 若仅在 DEV 出现，标注「仅开发环境，与本次发版无关」——解决 B4 的稀释问题

### F. 关键衰退指标：换掉主指标

**F1. 用"业务影响三档"替代差异率作主指标**

| 档位 | 判定依据 | 客户可见说法 |
|---|---|---|
| 🔴 阻断 | 元素遮挡/截断导致操作不可达、关键元素缺失、运行时报错 | 需要修复后才能验收 |
| 🟠 影响体验 | 可见错位、文案异常、控件渲染异常，但操作仍可完成 | 建议修复，可协商延期 |
| ⚪ 可忽略 | 整体位移、抗锯齿/字体渲染、测试数据变化 | 已确认无害，不需要你处理 |

> 映射规则：AI 审计的 `blocker→🔴`、`warning+高置信→🟠`、`noise/位置偏移/渲染→⚪`；像素层的 `appeared/vanished/内容变化` 交由 AI 层二次定性后再落档。

**F2. 差异率降级为"辅助信号"，默认折叠**
- 从卡片主数字降级为 `ⓘ 像素差异 0.70%` 的次要标签，并在阅读指南中明确写一句：**"百分比大小不代表严重程度，1% 的位移可能无害，0.1% 的按钮缺失可能是阻断。"**
- 这正好呼应 `ui-regression-report-for-customer.md` §3 已经写好的主张——把口径落实在 UI 上，而不是只写在文档里

**F3. 引入"有效质量覆盖率"，与"基线覆盖率"并列展示**

```
基线覆盖率  83%  （44/53 步有基线，9 步待建）
质量覆盖率  4%   （53 步中仅 4 步完成 AI 可用性审计，49 步未判定）
```

> 现在的 83% 会让客户以为"八成页面都验证过了"。把 AI 审计的 skipped 计入分母，才是诚实的口径，也反向推动补齐 selectors。

**F4. 首屏指标从 4 格改为 3 格 + 1 条结论**
- 现状：需要修复 / 可接受差异 / 完全一致 / 已对比步骤（4 个数字 + 覆盖率）
- 建议：**需要修复（🔴）/ 影响体验（🟠）/ 可忽略（⚪）** + 一句"9 步待建基线未参与判定"
- 把"已对比步骤"这种工程指标移入页脚

**F5. 增设"衰退趋势"微视图**
- 每个页面/流程附一条 5 次运行的档位色条（🔴🟠⚪⚪⚪），一眼看出"在好转还是在恶化"
- 替代 B3 那句语义含混的"状态恶化/改善"文字

### G. 呈现形式：问题驱动 + 证据折叠

**G1. 重构信息架构：从"页面平铺"到"问题优先"**

```
现状：结论速览 → [96 个页面卡片平铺] → 检测范围
建议：结论速览（一屏） → 需修复问题（每张卡一个问题） → 影响体验 → 可忽略（默认折叠） → 待建基线清单
```

- 一张卡 = 一个问题，证据（并排/标注/拖动/像素）**默认收起**，点开才加载——现报告 577KB / 96 组大图的问题即刻缓解
- "完全一致"的页面不再占用卡片位，压缩成一行"18 个页面与基线完全一致"

**G2. 统一四套状态术语，建立唯一映射表**

| 统一档位 | 像素回归 | AI 审计 | 内部 severity | CI gate |
|---|---|---|---|---|
| 阻断 | regress | fail | blocker | 失败 |
| 影响体验 | minor（actionable） | review（高置信） | warning | 通过 + 告警 |
| 可忽略 | minor（benign） | review（低置信）/ noise | noise / info | 通过 |
| 未判定 | uncovered | skipped | — | — |

> 关键改动：**把现在的 minor 一分为二**。这是解决 C3（遮挡与位移同档）的关键，也是让"需关注"真正有意义的唯一办法。

**G3. 卡片左上角性质标签与结论文案强制同源**
- 现状 A6 的根因是：标签取 `regions[].nature`，文案取 `reason` 模板，两者独立生成
- 建议：由同一份 `natureSummary`（如 `{dominant:'shift', shiftPx:9, contentIdentical:true}`）同时驱动标签、文案、框色，杜绝三处打架

**G4. 补充缺失的交互出口**
- 每条问题增加：`接受为新基线` / `提交缺陷` / `标记为预期变更`
- 报告末尾生成"验收签字区"：本次结论 + 确认人 + 日期，支持打印为 PDF 归档

### H. 通俗化叙述

**H1. 建立术语替换词典（渲染层统一过滤）**

| 现在的说法 | 换成 |
|---|---|
| 明显衰退 / regress / blocker | 需要修复 |
| 轻微变化 / minor | 有差异但不影响使用 |
| 位置偏移 9px | 内容整体右移了 9 像素，内容本身完全一样 |
| 渲染差异 | 显示效果差异（人眼看不出） |
| 监控区域文案一致 | 页面文字与上次验收一致 |
| 非样式回归 | 不是界面样式问题 |
| Stage9084环境 | 验收环境（Stage9084）|
| DEV环境 | 开发自测环境（仅供内部参考） |
| Golden 回归 | 核心流程回归 |

**H2. 一句话结论模板（首屏必现）**

```
本次验收：53 个页面完成比对，44 个有验收基线。
  → 0 个需要修复
  → 3 个影响使用体验，建议修复（其中 1 个为本次新增）
  → 23 个有差异但确认无害，不需要你处理
  → 9 个页面尚未建立验收基线，本次未参与判定
结论：未发现阻断问题，建议确认上述 3 项后发布。
```

**H3. 具象化换算**
- 差异率旁自动补一句：`0.70% ≈ 页面 1/140 的面积，约一张小图标大小`
- 位移量表述：`整体右移 9px ≈ 一根手指宽度的 1/8`

**H4. 阅读指南前置并直击痛点**
- 移到报告最顶部（结论之上），第一条就解释："本报告中『问题』按**根因**计数（16 个），『步骤』按**页面次数**计数（26 次），两者数字不同是正常的。"
- 或者直接删掉"根因/步骤"这对内部概念，全报告只保留一个计数口径

**H5. 交付形态补充**
- 除单文件 HTML 外，同时产出 **PDF（签字归档）** 与 **一段 200 字内的飞书/邮件摘要**（`customer-report-summary.json` 已有全部字段，直接模板化即可）
- HTML 内嵌一条提示：「本报告的对比图存放在 results/ 目录，转发时请一并打包」

## 优先级建议

| 优先级 | 事项 | 理由 |
|---|---|---|
