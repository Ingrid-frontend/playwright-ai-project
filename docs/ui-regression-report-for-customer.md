# UI 衰退检测报告 · 交付说明

> 面向对象：验收方 / 项目负责人。
> 交付物：`results/ui-regression-customer.html`（单文件，双击即可在浏览器打开，无需安装任何东西）。
> 生成命令：`npm run report:customer`

---

## 1. 这份报告回答什么

每次发版前，我们把当前页面截图与**已验收通过的基线截图**逐像素比对，回答三个问题：

1. 界面有没有出现不该有的变化？
2. 如果有，是哪个页面、哪块区域、严重到什么程度？
3. 哪些差异确认无害，不需要占用你的时间？

报告只做「当前 vs 验收基线」这一件事。历史运行对比、跨浏览器差异、内部稳定性指标都不在客户报告里，那些是我们工程团队自己排查用的。

---

## 2. 怎么读这份报告（三步）

**第一步：看首屏一句话结论**

顶部大字直接给结论，例如「发现 2 个 UI 问题需要处理」，副标题说明影响范围。下方四个数字是步骤级口径：

| 数字 | 含义 | 要不要处理 |
|---|---|---|
| 明显衰退 | 内容真的变了，可能影响使用 | **需要处理** |
| 轻微变化 | 差异范围很小，多为位置偏移或字体渲染不同 | 不需要 |
| 完全一致 | 与基线零差异 | 不需要 |
| 已对比步骤 | 本次实际做了像素比对的步骤数 | — |

> 「明显衰退」按**步骤**计数，问题清单按**根因**计数。同一处改动影响了 2 个步骤，会记 2 个衰退步骤、但只列 1 个问题，避免同一件事被重复汇报。

首屏结论栏按结论分三色：红色＝发现明显衰退（需要处理）；**琥珀色＝仅存在轻微变化（需关注，建议人工确认，多为位置偏移或字体渲染差异，内容一致）**；绿色＝完全一致、无衰退。琥珀不等于「有问题」，只是提示你瞄一眼再决定接受与否。

**第二步：扫「结论」页的问题清单**

一行一个问题，含页面名、问题描述、差异率、影响步骤数。整份报告的结论扫完这几行就够了。想看证据，点行尾的「看对比图」。

**第三步：在「对比明细」看图**

每个问题给三种视图：

- **标注变化**（默认）：在当前截图上直接框出变化区。**红实线框 = 需要处理的实质变化；灰虚线框 = 位移或渲染差异，内容一致。**
- **拖动对比**：左右拖动分隔线，同一位置对照基线与当前。
- **像素差异**：逐像素差异热点图，用于精确定位。

底部「检测范围」页列出本次全部检测项，包括尚无验收基线的步骤，用于确认覆盖面。

## 3. 分级口径：为什么「差异 1.23%」反而不用管

这是本次优化的核心。像素差异率**无法区分**「内容真的变了」和「同样的内容整体挪了几像素」——后者对使用者没有任何影响，但差异率可能比前者更高。

所以我们的判定以**变化性质**为第一依据，差异率只作辅助信号：

| 变化性质 | 判定方式 | 是否需要处理 |
|---|---|---|
| 新增内容 | 基线该位置是空白，当前出现了内容 | **需要处理** |
| 内容缺失 | 基线有内容，当前空了 | **需要处理** |
| 内容变化 | 对齐后内容仍然不同 | **需要处理** |
| 位置偏移 | 平移对齐后内容吻合（含 1px 级亚像素位移） | 不需要 |
| 渲染差异 | 仅抗锯齿/字体渲染级别，人眼不可见 | 不需要 |

判定顺序：先确认差异是否**人眼可见**（亮度变化超过阈值的像素占比），再尝试平移对齐。能对齐且残差接近零，就判为位置偏移并明确写出偏移量；对不齐才追究内容变化。分隔线、图标条这类细窄区域允许 1px 级亚像素位移残留，只要平移能明显压低残差就仍判为位置偏移。

> 红框只出现在「明显衰退」的问题卡里。被判为轻微变化的卡片一律用灰虚线标注，结论与标注不会互相矛盾。

**实测效果**（本项目最近一次全流程，16 个已对比步骤）：

```
优化前： 明显衰退 9 · 轻微变化 4   →  4 个问题分组，其中 4 个是误判
优化后： 明显衰退 3 · 轻微变化 10  →  2 个问题分组，全部为真实新增内容
```

被正确降级的典型案例：

- DEV管理员页面，差异 1.23% → 结论「页面中部右侧内容整体平移 9px，逐像素比对后内容完全一致，不是功能问题」
- 审批历史页面，差异 0.61% → 同类，整体平移 12px

被保留的真实问题：

- 我的审批，差异 1.04% → 页面下部新增了一块 950x10 的内容
- 返回步骤，差异 0.82% → 同一根因

## 4. 报告里刻意不放的东西

为了让报告能被直接读懂，以下工程内部信息已从客户报告中移除（引擎侧仍保留，工程团队用 `npm run compare-screenshots` 查看）：

| 移除项 | 原因 |
|---|---|
| 热力图矩阵（脚本 × 步骤） | 内部调试视图 |
| Visual Review（Approve/Reject + CLI 命令） | 基线维护工作台，不是交付内容 |
| 迭代历史 Tab | 客户只关心本次结果 |
| 跨浏览器 diff、浏览器筛选 | Chrome↔WebKit 差异是工程关注点 |
| 两次运行间对比（run-drift） | 内部稳定性信号，会与「衰退」概念混淆 |
| 原始对比表（compareKind / severity 等字段） | 工程师术语 |
| 无对比的裸截图堆叠 | 没有基线对照就没有信息量 |
| 样式取色、DOM 结构哈希、文本归一化维度 | 「某按钮 colorDelta=3」对验收无意义 |

同时清理的展示层问题：内部步骤名（`entry-goto`、`step-3`、`approval-list`）已翻译为中文页面名；运行时间戳目录名不再出现在页面上。

## 5. 视觉与文案规范

**配色**：红 `#e03131` 仅用于需要处理的问题；琥珀 `#f08c00` 用于无需处理的轻微变化；绿 `#2f9e44` 用于一致；灰 `#868e96` 用于位移/渲染框与未检测项。全报告只有红色代表「要动手」。

**层次**：首屏只放结论与速览清单（约一屏内可读完），大图证据全部收进「对比明细」；轻微变化默认折叠。

**文案原则**：不用「衰退」「blocker」「severity」这类词吓人或添堵，直接写清「哪里、什么变了、要不要处理」。位移类差异必须明确写出「内容完全一致」和具体偏移量。

---

## 6. 使用建议

1. **每次发版前跑一次**，把 HTML 作为验收附件归档。
2. 报告显示「未检测」的步骤，说明该页面还没建立验收基线。确认页面长相正确后，由我们执行基线固化，下次即纳入比对。
3. 若某处变化是**本次需求内的预期改动**，确认后固化为新基线，后续不再报出。
4. 报告为单文件 HTML，图片以相对路径引用 `results/` 目录，归档时请连同该目录一起保留。

---

## 7. 覆盖率口径说明（避免误读）

合格率 = 已对比步骤中无明显衰退的占比。**未建基线的步骤不计入分子也不计入分母**，会单独显示「N 步尚无验收基线，未参与判定」。我们不会用「未检测」来粉饰通过率。
