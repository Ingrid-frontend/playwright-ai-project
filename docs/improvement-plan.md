# Playwright AI 项目瓶颈突破改造方案

> 索引：[docs/README.md](./README.md)

> 编制日期：2026-09-15  
> 目标：识别核心瓶颈 → 提出可落地措施 → 分阶段实施 → 统一验收指标

## 一、现状分析

### 1.1 已验证的事实

| 维度 | 现状 | 证据 |
|------|------|------|
| 代码质量 | ESLint 0 errors / 124 warnings；TypeScript 全量通过 | `npm run lint` / `npm run typecheck` |
| CI 门禁 | Lint job 设 `continue-on-error: true`（非阻断）；Node 18 与 ESLint 10 要求 Node≥20 冲突 | `.github/workflows/docs-and-lint.yml` |
| 类型检查覆盖 | 根 `tsconfig.json` 仅含 src/tests/scripts/flow-kit，**不含三个 flow 目录** | `tsconfig.json` |
| Golden 数据 | 种子缺失时从实时列表回退读取，存在筛选残留风险 | `request-flow/tests/request/golden-regression.spec.ts:64-130` |
| 失败分类 | 所有非零退出均计为 flaky，环境阻断（如 SAFE_DELETE）被误判为业务不稳定 | `scripts/flow/run-golden-flake-check.ts:140-154` |
| 交付链路 | issues 新鲜度校验在 summary 显式传入时跳过；图片上传失败不阻断交付 | `scripts/feishu/write-bitable-report.ts:65-102`、`deliver-customer-report.ts:81-161` |
| Studio 运行 | `runNpmScript` 无超时；manifest 读写存在竞态（同 run 多次写 history） | `pw-files/lib/flow-run-common.js:21-52, 426-449` |
| 截图等待 | 13 个 antd 动画选择器串行等待，理论超时预算 19.5s | `src/utils/screenshot-wait.ts:20-38` |

### 1.2 核心结论

项目功能完备、代码质量基线良好，但**质量门禁覆盖不全、失败归因粗放、运行到交付链路不可追溯**，导致：
- 客户交付结果不可信（无法证明"本次运行无问题"）
- 环境问题被误判为用例不稳定，浪费排查时间
- Studio 交互与 CI 运行存在数据竞争风险

## 二、六大瓶颈与改造措施

### 瓶颈 1：质量门禁覆盖不全

**问题**：根 tsconfig 不含 flow 目录；CI lint 非阻断；Node 版本与 ESLint 要求冲突。

**措施**：
1. 根 `tsconfig.json` 增加 flow 目录引用，统一类型检查入口
2. CI lint job 移除 `continue-on-error`，改为阻断（先修复现有 warning 或设 warning 阈值）
3. CI Node 版本升级至 20（与 ESLint 10 对齐）

**预期效果**：任何 flow 目录类型错误在 PR 阶段即阻断；lint 问题不过夜。  
**优先级**：P0  
**验收标准**：
- `npm run typecheck` 覆盖全部 flow 目录
- CI lint 失败时 PR 不可合并

---

### 瓶颈 2：Golden 数据管理与失败分类

**问题**：种子缺失时回退读实时列表，筛选残留影响后续步骤；所有非零退出均计为 flaky。

**措施**：
1. 种子缺失时直接跳过并标记 `SEED_MISSING`，不从实时列表回退
2. `run-golden-flake-check.ts` 增加失败类型分类：
   - `BUSINESS_FLAKY`：业务逻辑不稳定
   - `ENV_BLOCKED`：环境阻断（SAFE_DELETE、网络超时等）
   - `SEED_MISSING`：种子数据缺失
   - `INFRA_FAIL`：基础设施故障
3. 仅 `BUSINESS_FLAKY` 计入 flaky 率

**预期效果**：flaky 率指标真实反映业务稳定性；环境阻断不再污染指标。  
**优先级**：P0  
**验收标准**：
- 环境阻断场景下 flaky 率为 0
- 种子缺失时测试跳过并在报告中标明原因

---

### 瓶颈 3：运行到交付链路不可追溯

**问题**：issues 新鲜度校验可被绕过；图片上传失败不阻断交付；无法证明"本次交付基于本次运行"。

**措施**：
1. `write-bitable-report.ts` 移除 summary 显式传入时的新鲜度跳过逻辑
2. `deliver-customer-report.ts` 图片上传失败时阻断交付并返回非零退出
3. 交付报告增加 `runId` + `generatedAt` 强绑定，接收方可校验时间戳

**预期效果**：每次交付可追溯到具体运行；交付失败有明确信号。  
**优先级**：P0  
**验收标准**：
- 交付报告包含 `runId` 和 `generatedAt`
- 图片上传失败时交付命令返回非零退出码

---

### 瓶颈 4：共享能力边界模糊

**问题**：`screenshot-wait.ts` 串行等待 13 个选择器，超时预算过高；`approval-list.page.ts` 构造函数注册响应监听无清理。

**措施**：
1. `screenshot-wait.ts` 改为并行等待（`Promise.all`），总超时收敛至 3s
2. `approval-list.page.ts` 增加 `dispose()` 方法清理监听器；`pendingHooked` 改为实例级而非类级

**预期效果**：截图等待时间从 ~19s 降至 ~3s；页面实例销毁后无内存泄漏。  
**优先级**：P1  
**验收标准**：
- 截图等待总耗时 < 4s
- 页面实例销毁后监听器数量归零

---

### 瓶颈 5：Studio 与 CI 运行数据竞争

**问题**：manifest 读写存在竞态；`runNpmScript` 无超时。

**措施**：
1. manifest 写入改用文件锁（`proper-lockfile`）或原子写入（写临时文件后 rename）
2. `runNpmScript` 增加超时参数（默认 10min），超时后 kill 子进程并返回错误
3. 同 run 内多次 manifest 写入合并为一次

**预期效果**：Studio 并发运行不产生重复 history 条目；长时间挂起的运行自动终止。  
**优先级**：P1  
**验收标准**：
- 并发运行 2 个 flow，history 文件无重复条目
- 超时场景下子进程被 kill 并返回错误码

---

### 瓶颈 6：协作流程与工具链对齐

**问题**：团队成员对"何时算完成"标准不一；PR 审查缺乏自动化辅助。

**措施**：
1. 定义 DoD（Definition of Done）：typecheck 通过 + lint 无新增 warning + 相关 flow 运行通过
2. PR 模板增加 checklist：是否影响 golden 种子、是否涉及交付链路、是否需要更新文档
3. 关键路径（交付、golden）变更需 2 人审查

**预期效果**：PR 审查标准统一；关键变更有双重保障。  
**优先级**：P2  
**验收标准**：
- PR 模板包含 checklist
- 关键路径变更 PR 有 2+ 审查通过

---

## 三、分阶段实施计划

### 第一阶段：基线建立（第 1 周）

**目标**：完成 P0 瓶颈改造，建立可信质量基线。

**关键任务**：
- [ ] 根 tsconfig 增加 flow 目录引用
- [ ] CI lint 改为阻断 + Node 升级至 20
- [ ] `run-golden-flake-check.ts` 增加失败分类
- [ ] Golden 种子缺失时跳过而非回退

**所需资源**：1 工程师 × 5 天  
**潜在风险**：
- CI Node 升级可能导致其他依赖不兼容 → 先在分支验证全量测试
- 失败分类逻辑变更可能影响现有报告 → 保留旧字段兼容

**应对策略**：
- Node 升级前在 CI 分支跑完整 flow 验证
- 失败分类新增字段，旧字段保留 1 个版本周期

---

### 第二阶段：可信交付（第 2-3 周）

**目标**：运行到交付链路完全可追溯，交付失败有明确信号。

**关键任务**：
- [ ] issues 新鲜度校验移除绕过逻辑
- [ ] 图片上传失败阻断交付
- [ ] 交付报告增加 `runId` + `generatedAt` 强绑定
- [ ] 交付链路端到端验证（运行 → 报告 → 飞书）

**所需资源**：1 工程师 × 10 天  
**潜在风险**：
- 移除绕过逻辑可能导致历史报告生成失败 → 先灰度验证
- 图片上传失败阻断可能因网络波动误杀 → 增加重试（3 次）

**应对策略**：
- 新鲜度校验先在 dry-run 模式验证 1 周
- 图片上传增加指数退避重试

---

### 第三阶段：降本增效（第 4-6 周）

**目标**：截图等待时间降低 80%；Studio 并发安全。

**关键任务**：
- [ ] `screenshot-wait.ts` 并行等待改造
- [ ] `approval-list.page.ts` 监听器清理
- [ ] manifest 写入原子化
- [ ] `runNpmScript` 增加超时

**所需资源**：2 工程师 × 15 天  
**潜在风险**：
- 并行等待可能遗漏某些动画 → 保留串行 fallback 开关
- manifest 原子写入在 Windows 可能不兼容 → 跨平台测试

**应对策略**：
- 并行等待增加环境变量开关，可回退串行模式
- manifest 写入使用 `fs.promises.rename`（POSIX 原子）

---

### 第四阶段：固化与扩展（第 7-8 周）

**目标**：协作流程标准化；为后续扩展（多环境、多浏览器）打基础。

**关键任务**：
- [ ] 定义 DoD + PR 模板
- [ ] 关键路径变更 2 人审查规则
- [ ] 多环境配置抽象（stage9084 / 其他环境）
- [ ] 跨浏览器截图对比开关（已有基础设施，需完善配置）

**所需资源**：1 工程师 × 10 天 + 团队评审  
**潜在风险**：
- 2 人审查可能拖慢紧急修复 → 设 SLA：24h 内必须审查
- 多环境抽象可能过度设计 → 仅抽象当前需要的差异点

**应对策略**：
- 紧急修复可先合并后补审查（标记 `hotfix` 标签）
- 多环境抽象仅覆盖 stage9084 + 1 个测试环境

## 四、统一验收指标

| 指标 | 基线（当前） | 目标（第 8 周） |
|------|-------------|----------------|
| 类型检查覆盖率 | src + tests + scripts | 全量（含 flow） |
| CI lint 阻断 | 否 | 是 |
| Flaky 率真实性 | 含环境阻断 | 仅业务不稳定 |
| 交付可追溯性 | 部分（可绕过） | 完全（runId 绑定） |
| 截图等待耗时 | ~19s | < 4s |
| Studio 并发安全 | 否（竞态） | 是（原子写入） |
| PR 审查标准 | 无统一 | DoD + checklist |

---

## 五、风险总览与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| CI Node 升级导致依赖不兼容 | 阻断合并 | 分支先跑完整 flow 验证 |
| 失败分类逻辑变更影响报告 | 历史数据不可比 | 新旧字段并存 1 个版本周期 |
| 图片上传阻断因网络波动误杀 | 交付失败率上升 | 指数退避重试 3 次 |
| 并行等待遗漏动画 | 截图不稳定 | 环境变量开关可回退 |
| 2 人审查拖慢紧急修复 | 交付延迟 | hotfix 标签可先合并后补审查 |

## 六、资源需求

- **人力**：2 名工程师（熟悉项目架构 + 有 CI/CD 经验）
- **时间**：8 周（含验证 + 灰度）
- **工具**：无新增工具需求（利用现有 GitHub Actions + 飞书）

## 七、成功标准

8 周后，项目应达到：
1. **可信**：任何交付结果可追溯到具体运行，客户可独立验证
2. **稳定**：flaky 率真实反映业务稳定性，环境问题不污染指标
3. **高效**：截图等待时间降低 80%，Studio 并发安全
4. **可扩展**：协作流程标准化，为多环境/多浏览器扩展打基础
